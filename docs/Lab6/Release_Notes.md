## Можливості

Авторизація і ролі admin/keeper/manager, каталог і пошук, надходження, списання, аудит, довідники, адміністрування користувачів та збереження даних SQLite. Ролі застосунку не є учасниками розробки.

## Виправлення DEF-01

Повтор keyed надходження або списання більше не змінює залишок удруге. Одночасні дублікати серіалізуються SQLite, повертається початкова відповідь. Змінений JSON або тип із тим самим ключем дає 409. React зберігає ключ після втрати відповіді. Перевірки ролі та CSRF виконуються до читання кешованої відповіді.

## Запуск і оновлення даних

Потрібен Python 3.11+. Для локальної демонстрації: розпакувати EasyStock, запустити run_demo.bat у Windows або bash run_demo.sh у Linux/macOS; відкрити http://127.0.0.1:5000. Node.js не потрібен для запуску готового frontend/dist. Перший запуск потребує мережі для Python-залежностей.

Перед оновленням зупинити сервер і зберегти резервну копію SQLite разом із потрібними WAL/SHM після коректного завершення процесу. start.py виконує db.create_all і додає нову таблицю stock_requests. Старі таблиці не переписуються; збереження даних перевірене на тестовій старій схемі. Для довільної зміни колонок потрібен окремий план міграції.

Запуск без --demo не створює стандартних облікових записів; це перевірено реальним HTTP-процесом і users=0. Для власних даних створюють першого адміністратора через flask --app backend/app create-admin з власним паролем. Відомі демонстраційні паролі застосовують тільки у локальній демобазі. Для зовнішнього доступу потрібні окремі налаштування HTTPS і безпечних cookie.

## Відомі обмеження

1. Верстка та критичний потік у Chromium/Firefox і Windows для нового коміту не перевірені. Знімки автора від 18.10.2026 стосуються попереднього запуску і не замінюють такої перевірки.
2. Незалежного людського review або перехресної сесії не проведено; є власна самоперевірка.
3. Idempotency-Key необов’язковий для старих API-клієнтів. Без нього автоматичний повтор запису не захищений. Для ключа потрібні той самий автор, тип і незмінений JSON.
4. UI тримає ключ у пам’яті компонента. Після закриття/перезавантаження форми та невідомого результату спочатку перевіряють історію.
5. Збережені ключі не мають автоматичного строку очищення; обсяг таблиці росте зі складськими операціями. База та резервні копії потребують контролю розміру.
6. Локальний SQLite і limiter у пам’яті одного процесу не перевірені як багатосерверна виробнича конфігурація. Тест навантаження не замінює профілювання реального складу.
7. Перевірка секретів базується на заданих високоточних шаблонах у текстових Git-об’єктах; бінарні історичні файли не досліджувалися як сховища довільних секретів.

## Rollback

Зупинити сервер і заборонити нові записи на час відновлення. Зберегти поточну базу окремою копією. Попередній стан коду — commit `0eabc81b33955948421838e0a98db920a799a640` (також локальний тег lab6-baseline у bundle). Повернути код командою `git switch --detach 0eabc81b33955948421838e0a98db920a799a640` або взяти попередній архів. Нова таблиця може залишатися: старий код її не використовує. Відновлювати базу з резервної копії потрібно лише за пошкодження чи несумісності, враховуючи втрату змін після дати копії. Після запуску перевірити health, вхід, залишок та історію на копії даних. Старий код не має захисту DEF-01, тому невідомі POST не повторюють без перевірки історії.
