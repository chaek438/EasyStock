# Ретроспектива EasyStock

Виконав: Бондаренко Сергій

Дата: 04.11.2026. Формат: індивідуальна ретроспектива на підставі артефактів лабораторних №1–6 та повторного технічного прогону. Інших учасників, голосування та відгуків викладача не було. Подальші дії є планом наступної ітерації.

## Start Stop Continue

| Категорія | Спостереження | Подальша практика |
|---|---|---|
| Start | DEF-01 виявив потребу в окремому сценарії повтору запису. | Уточнювати повтори, часткову відмову й права до початку зміни. |
| Start | Сценарії двох браузерів та людського огляду ще не виконані. | Планувати перевірку цільового обладнання до релізу. |
| Stop | Повтор POST без ключа може дублювати складський ефект. | Припинити сліпий повтор невідомої операції, спочатку перевіряти історію. |
| Stop | HTTP/DOM не перевіряє верстку реального браузера. | Не позначати невиконані методи тестування як Pass. |
| Continue | Ізольовані SQLite та seed дають передбачуваний старт. | Зберігати окремі дані для демо і тестів. |
| Continue | Матриця і датовані журнали пов’язують результат із кодом. | Зберігати release notes, теги, протоколи та відомі межі. |

## П’ять уроків

### 1 Повтор запису потребує окремого критерію приймання

Факт: У DEF-01 повтор надходження давав 57 замість 37, а повтор списання 11 замість 14.

Причина: Звичайний успішний POST не перевіряє ситуацію, коли відповідь загубилася після commit.

Наслідок: Без захисту залишок та історія змінювалися вдруге.

Урок: Для операції з побічним ефектом треба окремо визначити поведінку повтору.

Дія: До наступної зміни складської операції додати сценарій втрати відповіді та повтору в Definition of Ready.

Доказ: docs/Lab6/Defects.md, TC-07, TC-08. Відповідальний: Бондаренко Сергій. Критерій завершення: Описано ключ, незмінний JSON і очікуваний один рух.

### 2 Цілісність перевіряється разом з аудитом

Факт: Тести охоплюють відмову між зміною залишку й записом історії та конкурентні списання.

Причина: Перевірка лише числа на екрані не доводить узгодженість кількох таблиць.

Наслідок: Транзакція та умовний SQL-запис зберігають коректний стан під час помилки.

Урок: Тест має перевіряти всі пов’язані зміни та відкат.

Дія: Перед наступним релізом запускати TC-13, TC-15 і TC-16 як обов’язкову регресію.

Доказ: tests/test_api.py, tests/test_release.py. Відповідальний: Бондаренко Сергій. Критерій завершення: Після відмови не з’являється частковий документ або рух.

### 3 Готовий архів має запускатися без Git

Факт: У лабораторній №6 перевірено запуск із ZIP у середовищі без Git. Готовий frontend входить до релізу.

Причина: Середовище викладача може відрізнятися від середовища розробки.

Наслідок: Інструкція та перевірки не залежать від наявності робочого Git-клону.

Урок: Потрібно перевіряти саме формат, який отримує користувач.

Дія: Для кожного наступного релізу перевіряти розпакований ZIP на окремій демобазі.

Доказ: docs/Lab6/evidence/zip-without-git.json. Відповідальний: Бондаренко Сергій. Критерій завершення: Запуск, health, вхід і критичний сценарій проходять з архіву.

### 4 Автоматизація має чітку межу доказовості

Факт: HTTP та React DOM перевірки проходять. Сценарії Chromium/Firefox і незалежний людський walkthrough залишаються Not run.

Причина: DOM-тест не вимірює реальне відображення у браузері або зрозумілість інтерфейсу людині.

Наслідок: У документації вказано окремі статуси замість загального твердження про повну перевірку.

Урок: Висновок про якість треба обмежувати фактично виконаним методом.

Дія: Перед наступним показом пройти критичний потік у Chromium і Firefox та записати версії й результати.

Доказ: docs/Lab6/TestCases.md, TC-24, TC-25. Відповідальний: Бондаренко Сергій. Критерій завершення: Є датований протокол двох браузерів і окремий протокол людського огляду.

### 5 Матеріали захисту повинні посилатися на зафіксований реліз

Факт: Код v1.0.0 має визначений відбиток SHA-256. Матеріали №7 не змінюють виконуваний код.

Причина: Непомітна зміна коду після показу робить результати тестування неоднозначними.

Наслідок: Версію, докази та межі можна зіставити без пересування публічного тегу.

Урок: Потрібно зберігати показану версію, а виправлення видавати окремою версією.

Дія: Наступне виправлення коду оформити новим тегом і release notes з повторною регресією.

Доказ: docs/Lab6/Release_Notes.md, evidence/release-recheck.json. Відповідальний: Бондаренко Сергій. Критерій завершення: Попередній тег збережено, нові докази вказують на нову версію.
