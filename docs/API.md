# REST API EasyStock

Base URL: `http://127.0.0.1:5000/api`. Відповіді — JSON. Для операцій запису: `Content-Type: application/json`, cookie `easystock_session` та заголовок `X-CSRF-Token`, повернутий `auth/login` або `auth/me`. Токен сеансу не зберігається у localStorage. Login не вимагає CSRF, cookie має SameSite=Strict.

| Метод | Шлях | Доступ | Результат |
|---|---|---|---|
| GET | /health | Усі | Перевірка сервера |
| POST | /auth/login | Усі | `{email,password}` → `{user,csrf_token}` + HttpOnly cookie |
| GET | /auth/me | Авторизовані | Поточний користувач і CSRF |
| POST | /auth/logout | Авторизовані | Відкликання сеансу |
| GET | /dashboard | Авторизовані | Показники, low_products, recent, activity |
| GET | /products | Авторизовані | Пошук і пагінація |
| GET | /products/:id | Авторизовані | Деталі товару |
| POST | /products | Admin | Створення із stock=0 |
| PUT | /products/:id | Admin | Повна заміна полів каталогу |
| DELETE | /products/:id | Admin | Архівація при stock=0, історія збережена |
| GET | /categories, /suppliers | Авторизовані | `{items:[…]}` |
| POST | /categories, /suppliers | Admin | Створення |
| PUT | /categories/:id, /suppliers/:id | Admin | Редагування |
| DELETE | /categories/:id, /suppliers/:id | Admin | Видалення незв’язаних записів |
| POST | /stock/receipt | Admin, Keeper | Надходження, stock + audit + receipt |
| POST | /stock/writeoff | Admin, Keeper | Списання із перевіркою залишку |
| GET | /stock/history | Авторизовані | Історія та пагінація |
| GET, POST | /users | Admin | Список / створення |
| PUT | /users/:id | Admin | Поля, роль, активність, новий пароль |

Пагінація: `page=1`, `per_page=25` (максимум 100), відповідь `{items,total,page,per_page}`. Каталог: `q`, `category_id`, `status=available|low|empty`. `available` означає вище мінімального залишку; `low` включає нуль. Історія: `q`, `product_id`, `type=receipt|writeoff`, `from=YYYY-MM-DD`, `to=YYYY-MM-DD`. Дати фільтрів — UTC, межі дат включні; відображення часу — у локальній зоні браузера.

Товар:

```json
{"name":"SSD Kingston A400 480 GB","sku":"SSD-480","category_id":1,"supplier_id":1,"price":1450,"min_stock":5,"unit":"шт."}
```

Надходження:

```json
{"supplier_id":1,"items":[{"product_id":1,"quantity":20,"price":1250.50}],"note":"Накладна 001"}
```

Допускається скорочена форма `{product_id,quantity,price?,supplier_id?,note?}`. До 50 різних товарів. Якщо supplier_id не задано, береться постачальник першого товару. Ціна — закупівельна на момент надходження; не змінює ціну каталогу. Номер документа повертається як `receipt_id`.

Списання:

```json
{"product_id":1,"quantity":3,"note":"Продаж"}
```

Відповідь успіху складської операції (201):

```json
{"message":"Надходження збережено.","receipt_id":13,"items":[{"product_id":1,"quantity":37}]}
```

`items[].quantity` у відповіді — **новий залишок**, а не кількість руху.

Категорія: `{name}`. Постачальник: `{name,phone?,email?}`. Користувач: `{name,email,password,role}`; PUT також підтримує `active`. Ролі: `admin|keeper|manager`. Мінімум 8 символів пароля. Ніколи не повертаються хеші чи паролі.

Помилки: `{error:"Зрозуміле повідомлення"}`; 400 — валідація, 401 — відсутній/прострочений сеанс, 403 — роль/CSRF, 404 — запис відсутній, 409 — конфлікт або недостатній залишок, 429 — забагато спроб входу, 503 — БД тимчасово недоступна. При будь-якій помилці транзакція відкатується.

Сума грошей зберігається цілим числом копійок. Кількість — ціле число від 1 до 1 000 000 000 для руху; залишок від 0 до 1 000 000 000. SKU нормалізується у верхній регістр; назви шукаються через Unicode casefold, `%` і `_` трактуються буквально.


## Повтор складського запиту

POST /api/stock/receipt і /api/stock/writeoff приймають необов’язковий Idempotency-Key: 1–128 символів A-Z, a-z, 0-9, крапка, дефіс або підкреслення. Новий намір отримує новий ключ. Повтор з тим самим автором, типом і незміненим JSON повертає початковий JSON зі статусом 201 та не змінює склад удруге. Змінені дані або тип з уже збереженим ключем дають 409. Роль і CSRF перевіряються для кожного повтору. За відхилення чи rollback ключ не зберігається. Ключ, відповідь, склад і аудит фіксуються однією SQLite транзакцією та зберігаються після перезапуску.

Без ключа кожний POST залишається новою операцією за попереднім контрактом. Ключі автоматично не очищуються. React тримає ключ у пам’яті поточної форми; після її перезавантаження і невідомого результату потрібно звірити історію перед новим проведенням. Докладні докази наведені у Lab6/README.md.

## Кілька складів і документи з версії 1.1.0

`warehouse_id` вибирає склад у запитах до каталогу, картки товару та огляду. Без параметра використовується Основний склад (`1`). `GET /stock/history` без параметра повертає рухи всіх складів. У швидких `POST /stock/receipt` та `POST /stock/writeoff` склад задається полем `warehouse_id` у JSON; якщо його немає, діє Основний склад. Нові швидкі операції також повертають `document_id`. Повтор ключа з іншим складом є іншим наміром і повертає 409.

Картка й список товарів повертають `stock_revision`. Рухи містять `warehouse_id`, `warehouse`, посилання `document_id` та знакову зміну `delta`. Типи доповнено `transfer_out`, `transfer_in`, `adjustment_out`, `adjustment_in`, `reversal_out`, `reversal_in`. Склад і документ можна фільтрувати; старі рухи мають `document_id: null`.

| Маршрут | Доступ | Призначення |
| --- | --- | --- |
| `GET /warehouses` | Усі авторизовані | Склади, одиниці, товарні позиції в наявності, оцінка за цінами каталогу |
| `POST /warehouses`, `PUT /warehouses/:id` | Адміністратор | Створення з `code`, `name`, `address`; редагування назви й адреси |
| `GET /documents`, `GET /documents/:id` | Усі авторизовані | Список з фільтрами `warehouse_id`, `kind`, `status`, `number`; деталі з позиціями та рухами |
| `POST /documents`, `PUT /documents/:id` | Адміністратор або комірник | Створити чернетку або змінити власну; адміністратор може редагувати чужу |
| `POST /documents/:id/submit`, `POST /documents/:id/cancel` | Автор або адміністратор | Передати на погодження або скасувати до проведення |
| `POST /documents/:id/post`, `POST /documents/:id/return` | Адміністратор | Провести погоджуваний документ або повернути в чернетку |
| `POST /documents/:id/reverse` | Адміністратор | Створити сторно з `note`, зберегти первинний документ |
| `POST /data/catalog/preview`, `POST /data/catalog/import` | Адміністратор | Перевірити CSV із поля `csv`, додати нові товари, якщо всі рядки коректні |
| `GET /data/catalog-template.csv`, `GET /data/backup` | Адміністратор | Шаблон імпорту і копія SQLite для окремого відновлення |
| `GET /data/catalog.csv`, `GET /data/stock.csv`, `GET /data/history.csv` | Усі авторизовані | Експорт CSV; залишки й журнал можна обмежити складом |

Наприклад, чернетка переміщення:

```json
{"kind":"transfer","warehouse_id":1,"destination_id":2,"items":[{"product_id":1,"quantity":5}],"note":"Поповнення резерву"}
```

Типи чернеток: `receipt`, `writeoff`, `transfer`, `count`; до 50 різних товарів. Для рахунку `count` поле `quantity` означає фактичний підрахунок (допустимий нуль), `note` обов’язкове. Якщо рядок передає `stock_revision`, під час збереження сервер звіряє його з поточною версією залишку. Під час проведення перевіряється збережена версія і записується тільки різниця. У разі руху після підрахунку повертається 409, і весь документ залишається непроведеним.

Оновлення та переходи отримують `revision` останньої прочитаної версії документа. Погодження, проведення і сторнування не змінюють старі рухи. Повтор успішного `post` повертає проведений документ, повтор `reverse` — вже створений зворотний документ. Повтор не змінює кількості удруге. Докладний сценарій запуску та відновлення наведено в [описі етапу 1](Phase1/README.md).
